# Spec: Vote Explorer — Full Roll Call Data on the Site

## Problem

The raw vote data exists in `data/votes/*.json` (42 councillor files, every vote since 2011) but there's no way for users to browse it. Meeting pages show transcripts but not vote breakdowns. Councillor pages show summary stats but not individual votes. Users (like Luis from the Facebook thread) want "a full list of every motion and how each councillor voted."

## Solution

Add vote roll call data to **three places** on the site:

### 1. `/votes` — Master Vote Explorer Page

A new top-level page listing every motion with full roll call data.

**Features:**
- Reverse-chronological list of all motions (most recent first)
- Each entry shows: date, meeting name, item title, motion text (truncated), result, vote count
- Expandable/collapsible roll call: click to see YEA/NAY/ABSENT lists with councillor names
- **Filters:**
  - By date range (year picker or month picker)
  - By meeting type (Council, committee dropdown)
  - By result (passed/failed)
  - By councillor (show only votes a specific councillor participated in)
  - By contested/unanimous toggle
  - Search by keyword (matches item title and motion text)
- **Pagination:** 50 votes per page (there are ~15,000+ total votes)
- Visual indicator for close votes (margin ≤ 3)
- Link to the meeting page and eScribe source for each vote

**Data source:** New aggregated file `data/votes/_all-motions.json` generated by an updated `generate-votes.ts` script. Groups votes by (date, meeting, item, motionText) and collects all councillor votes into a single record.

### 2. Meeting Pages — Vote Breakdown Section

Each meeting page (e.g., `/months/2026-03/2026-03-03 - Council`) gets a new "Votes" section.

**Features:**
- Listed after the existing meeting content/transcript
- Each agenda item that had a vote shows:
  - Item number and title
  - Motion text
  - Result (e.g., "Motion Passed 11-4")
  - Expandable roll call (YEA/NAY/ABSENT with councillor name links)
- Grouped by agenda item, ordered by item number
- Visual tag for unanimous vs contested

**Data source:** The meeting markdown files get vote data injected during `generate-pages.ts` build step, reading from the same aggregated motions data.

### 3. Councillor Pages — Full Vote History

Each councillor page (e.g., `/councillors/current/s-trosow`) gets a "Full Vote History" section.

**Features:**
- Below the existing "Notable Dissenting Votes" section
- Expandable section: "View all X votes"
- Reverse-chronological list of every vote they cast
- Each entry: date, meeting, item title, their vote (YEA/NAY/ABSENT), result
- Filter by: year, committee, their vote (yea/nay only), contested only
- Colour coding: green for yea, red for nay, grey for absent
- Paginated (50 per page) since some councillors have 3,000+ votes

**Data source:** Existing `data/votes/{slug}.json` files, rendered into the markdown during `generate-pages.ts`.

## Implementation Plan

### Phase 1: Data Aggregation (generate script)

Update `scripts/generate-votes.ts` to also produce `data/votes/_all-motions.json`:

```typescript
interface AggregatedMotion {
  id: string;           // hash of date+meeting+item+motionText
  date: string;
  meetingSlug: string;
  meetingTitle: string;
  meetingType: string;
  meetingUrl: string;
  itemNumber: string;
  itemTitle: string;
  motionText: string;
  result: string;
  passed: boolean;
  unanimous: boolean;
  yeas: string[];       // councillor names
  nays: string[];
  absent: string[];
  margin: number;       // |yeas| - |nays|
}
```

### Phase 2: Vote Explorer Page

**New files:**
- `content/votes.md` — frontmatter + shell content for the page
- `quartz/components/VoteExplorer.tsx` — React component with filtering, search, pagination
- `quartz/components/VoteRollCall.tsx` — Reusable expandable roll call component

**Note:** Quartz is a static site generator. The filtering/search must be **client-side JavaScript** since there's no server-side rendering for content pages. The full `_all-motions.json` is large (~15K motions) so we need either:
- Option A: Pre-split into monthly JSON files, lazy-load on scroll/filter change
- Option B: Ship the full JSON but compressed (gzip should bring it from ~5MB to ~500KB)
- Option C: Only ship the last 2 years by default, load more on demand

Recommend **Option A** (monthly files) for best performance.

### Phase 3: Meeting Page Vote Sections

Update `scripts/generate-pages.ts` (or `add-transcripts-to-pages.ts`) to inject vote data into meeting markdown files during build.

For each meeting, find all motions from `_all-motions.json` matching that date+meeting, and append a "## Votes" section to the markdown with formatted roll calls.

### Phase 4: Councillor Full History

Update `scripts/generate-pages.ts` councillor section to append a "## Full Vote History" section with all their votes, using a collapsible format to keep page size manageable.

Since some councillors have 3,000+ votes, this section should use `<details>` tags grouped by year.

## Open Questions

1. **Performance:** Full vote data for all years is huge. Should we limit the `/votes` page to current term (2022-2026) by default with a "Load older" option?
2. **Councillor links:** Should councillor names in roll calls link to their profile pages? (Yes, probably.)
3. **Topic tags:** Should we add topic tags to votes now (for the future topic index feature) or do that separately?
4. **Mobile:** Roll call tables on mobile need careful handling. Maybe stack vertically instead of side-by-side YEA/NAY columns.

## Priority Order

1. **Meeting pages** — easiest win, most natural place users look
2. **Vote explorer** — the big new feature
3. **Councillor full history** — extends existing pages

## Estimated Effort

- Phase 1 (data aggregation): 2-3 hours
- Phase 2 (vote explorer): 6-8 hours (most complex — client-side filtering, pagination, search)
- Phase 3 (meeting pages): 3-4 hours
- Phase 4 (councillor history): 2-3 hours

Total: ~15-18 hours of work, spread across a few PRs.
